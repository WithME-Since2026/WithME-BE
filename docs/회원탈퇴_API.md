# 회원탈퇴 사유·의견 저장 (#43)

## 담당 범위

#43은 `user_withdrawals` 테이블과 사유·추가 의견 저장 서비스만 제공한다.
회원탈퇴 API, 계정 비활성화·복구, 모임장 위임, 모임·참석 기록 정리, 토큰 삭제와 카카오 unlink는 #42 담당 범위다.
#43에는 별도 HTTP API가 없다. #42의 URL·응답 형식·계정 및 모임 정책을 변경하지 않는다.

## #42 서비스 연동

`WithdrawalFeedbackService`를 주입하고 기존 회원탈퇴 트랜잭션 안에서 호출한다.

```java
withdrawalFeedbackService.createFeedback(
        userId,
        new WithdrawalFeedbackRequest(reason, opinion)
);
```

- 사유 `reason`: 선택, 최대 100자
- 추가 의견 `opinion`: 선택, 최대 1,000자
- `userId`: 필수 양수, #42에서 인증된 사용자 ID를 전달한다.
- 서비스 메서드 검증으로 길이·null 요청·잘못된 사용자 ID를 거부한다.
- `Propagation.MANDATORY`를 적용해 호출자의 트랜잭션에 참여하며, 트랜잭션 없는 호출은 거부한다.
- 이후 회원탈퇴 처리에서 예외가 발생하면 저장한 사유·의견도 함께 롤백된다.
- 원문은 로그에 남기지 않는다.
- 복구 후 재탈퇴하는 #42 정책에 맞춰 동일 사용자의 여러 탈퇴 이력을 허용한다.

#42 요청 DTO의 `opinion` 전달과 위 서비스 호출은 #42 구현에서 연결해야 한다. 이 브랜치 단독으로는 탈퇴 의견이 자동 저장되지 않는다.

## 스키마

Flyway `V16__create_user_withdrawals.sql`은 아래 테이블과 사용자 ID 인덱스를 추가한다.

| 컬럼 | 설명 |
|---|---|
| withdrawal_id | 탈퇴 이력 PK |
| user_id | users FK, 중복 허용 |
| reason | 선택 사유, VARCHAR(100) |
| opinion | 선택 추가 의견, VARCHAR(1000) |
| created_at / updated_at | 저장·수정 시각 |

기존 develop에 중복 V9/V10 migration 파일이 있으므로 배포 전 기존 정리 정책을 확인해야 한다.
#43이 아직 적용되지 않은 개발 브랜치인 상태에서 V16을 수정했다. 적용된 환경이 있다면 후속 migration으로 전환해야 한다.

## 확인 항목

1. 회원탈퇴 트랜잭션에서 사유·의견이 저장되는지 확인한다.
2. 사유 없이 호출해도 저장되는지, 길이 초과는 거절되는지 확인한다.
3. 계정 복구 후 다시 탈퇴했을 때 같은 사용자의 이력이 추가되는지 확인한다.
4. 호출자 트랜잭션 롤백 시 이력도 남지 않는지 확인한다.
5. 서비스 호출이 계정·모임·참석 기록·토큰을 직접 변경하지 않는지 확인한다.

운영 PostgreSQL/Flyway 실행은 별도 검증이 필요하다.

## 로컬 검증 결과 (2026-11-01)

기존 테스트와 임시 저장 검증 4개를 실행했다. 선택 사유 및 재탈퇴 이력 저장, 입력 검증,
호출자 롤백 시 이력 롤백, 트랜잭션 없는 호출 거부를 모두 통과했다. 계정 정보와 알림 설정이 변경되지 않는지도 확인했다.
H2 DB를 사용하고 Redis 저장소를 대체했다. 검증 코드는 build 아래에 두어 커밋하지 않았다.
